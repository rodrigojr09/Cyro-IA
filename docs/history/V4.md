# JARVIS v4 — implementação e validação local

Data: 22/10/2026. Versão alvo: 4.0.0. Após a validação local, o proprietário autorizou o envio à nuvem e a compilação do instalador. A execução e o resultado dessa publicação são registrados abaixo; não há autorização automática para futuras publicações.

## Comportamento

- Cloud somente administrativo e APIs: a raiz usa o layout autenticado, sem página pública. Login administrativo em `/login`, sem cadastro público. Removidas as telas de ativações/licenças e a API de ativação.
- Administradores cadastram e-mail e senha, alteram a senha e liberam/bloqueiam o usuário. Desativação e troca de senha invalidam sessões. Usuários existentes sem senha recebem uma pelo painel.
- Desktop inicia no login e somente cria workspace e Quick Chat após uma sessão validada. E-mail/senha são enviados via HTTPS em produção; a senha não é persistida. A sessão opaca fica protegida pelo safeStorage do Windows, com somente seu HMAC no Cloud.
- Login automático exige validação online na abertura. A sessão é verificada a cada cinco minutos. Erros de validação retornam ao login e destroem Quick Chat; falha de rede preserva a sessão protegida e permite recuperação após nova validação. Logout apaga a sessão salva e revoga a sessão Cloud quando disponível.
- Fechar a janela principal encerra o aplicativo e seu backend próprio. A antiga preferência de manter na bandeja é ignorada. Minimizar continua mantendo a janela e o Quick Chat abertos.
- Confirmações humanas e IPC restrito continuam ativos. OpenAI/PostgreSQL permanecem exclusivamente no Cloud. `Backup/` não foi alterado.

## Migração

A migration `20261022000000_desktop_login` adiciona associação entre Session e Device com integridade por usuário, remove as antigas credenciais persistentes de Device e revoga códigos legados. Cadastros, uso, auditoria e tabelas históricas de licenças são preservados; códigos/licenças não autorizam a v4. O arquivo de ativação da v3 não é carregado. Aplicar migrations antes do uso contra um Cloud atualizado. Em 22/10/2026, ao iniciar o ambiente local após a configuração privada fornecida pelo proprietário, a migration v4 foi aplicada ao banco Cloud configurado. O histórico remoto também contém `20261021160000_public_site_settings`, ausente do checkout; esse histórico foi preservado, sem reset.

## Limpeza solicitada do Cloud

Escopo autorizado: apagar usuários EMPLOYEE, dispositivos, sessões, consumo, orçamentos, auditoria, códigos/licenças antigos e rate limits; preservar contas ADMIN/SUPER_ADMIN e configurações globais. Sessões administrativas também são encerradas, exigindo novo login. O comando recusa limpar se não houver SUPER_ADMIN ativo com senha, usa transação e verifica as contagens antes de confirmar. Não existe endpoint HTTP de limpeza.

```powershell
# Somente prévia de contagens; configure DATABASE_URL privadamente em cloud/.env.
npm run db:reset-users -w @jarvis/cloud
# Aplicação do escopo autorizado:
npm run db:reset-users -w @jarvis/cloud -- --apply
```

Limpeza real executada em 22/10/2026 após configuração privada da conexão e autorização do proprietário: preservada 1 conta administrativa; removidos 3 usuários comuns, 4 dispositivos, 4 sessões e 27 registros de uso. A transação também limpou clientes, orçamentos, auditoria, códigos/licenças antigos e rate limits. Verificação independente após o commit confirmou essas tabelas vazias e o administrador preservado. Configurações globais foram preservadas; nenhum banco local do Desktop foi limpo. Nenhuma credencial foi registrada ou publicada. A limpeza não aplicou migrations nem implantou a v4; posteriormente, para iniciar o ambiente local solicitado, foi aplicada a migration de sessões v4.

## Inicialização local solicitada

`start.bat` agora chama `tools/start_local.py` para iniciar Cloud e Desktop juntos. O Cloud usa localhost:3000 e APP_ORIGIN local no processo; o Desktop só é iniciado após resposta HTTP 200 da página de login. Ao encerrar, são finalizados apenas os processos criados pelo iniciador. Porta ocupada é informada sem fechar serviços existentes; o ambiente Desktop não recebe segredos OpenAI/PostgreSQL. Não há instalação automática ou migration no iniciador.

Validação do iniciador: 21 testes Python (`test_start_local` e `test_start`) aprovados, cobrindo ordem de inicialização, limpeza, falha do Cloud, porta ocupada e isolamento de segredos. Execução real de `start.bat` abriu Electron e retornou 200 no Cloud e no backend v4. Após interromper o teste, portas 3000/8765 e janela do JARVIS ficaram encerradas.

Cloud de desenvolvimento iniciado em `http://localhost:3000`, com APP_ORIGIN local definido apenas no processo. Desktop iniciado pelo supervisor Cloud, aberto na tela de login; backend local respondeu 200 com versão 4.0.0 e página de login Cloud respondeu 200. Banco, segredo de sessão e configuração OpenAI estão presentes no arquivo privado, sem exposição dos valores. A autenticação com senha real do usuário e chamadas pagas não foram executadas. Nenhum push ou deploy foi realizado.

## Correção de acesso administrativo ao Desktop

Correção adicional da finalização de login: em desenvolvimento, o Electron usava AppData/Roaming e o backend usava AppData/Local. Isso permitia autenticação Cloud 200, mas impedia publicar a sessão no serviço local. O Electron de desenvolvimento agora resolve a mesma pasta LocalAppData/JARVIS do backend; overrides explícitos e o caminho da edição instalada são preservados. Falhas posteriores à autenticação agora informam problema no serviço local em vez de acusar senha inválida. Não foram movidos nem apagados perfis anteriores.

Regressão: 70 testes Node do Desktop e 21 testes Python do iniciador aprovados. O novo `npm run test:session-electron -w jarvis-desktop` exercita a entrada Electron de produção, login com Cloud simulado, safeStorage, publicação da sessão em FastAPI real, acesso ao workspace por IPC e abertura do Quick Chat, com diretório temporário e sem chamadas pagas. Desktop e backend resolvem seus diretórios independentemente, reproduzindo o cenário do start.bat.

ADMIN e SUPER_ADMIN ativos também podem entrar no Desktop com as credenciais do painel. O login cria o perfil Client dentro da mesma transação, após verificar a senha e revalidar o acesso; não é necessária nova migration ou alteração do papel da conta existente. A política de sessões aceita os três papéis conhecidos e mantém bloqueio de contas inativas, dispositivo revogado e sessão expirada. Sessão de navegador sem dispositivo continua sem autorizar as APIs Desktop; sessão Desktop continua sem autorizar o painel.

Os 17 testes Cloud incluem senha incorreta/conta bloqueada sem provisionamento de perfil, primeiro login administrativo sem Client, sessão, renovação, bloqueio e logout para ADMIN e SUPER_ADMIN. PGlite confirma que as relações Client/Device/Session suportam uma conta administrativa sem mudar seu papel. A senha real do proprietário não foi lida nem usada nos testes.

Após a correção administrativa: TypeScript e build de produção aprovados, 8 testes Python de integração Cloud e duas verificações Electron reais (login com Cloud simulado e interface principal) aprovados. Cloud local e Desktop reiniciados; página de login e health do backend responderam 200, e Desktop abriu na tela de login. Nenhum push ou deploy.
